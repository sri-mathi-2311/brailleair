BrailleAir Project Report

Project name: BrailleAir

Report date: 11 April 2026

Report style: Simple English

Goal: Check what the project uses, what result it gives, how it works, whether it works offline and online, and whether an LLM is integrated.

1. Project Summary

BrailleAir is a Python-based assistive technology project. It takes an image of printed text, reads the text using OCR, changes the text into Tamil, converts the result into a Braille-like 5-bit vibration pattern, and then sends or simulates vibration commands for a tactile device.

The project also includes a web API and a React frontend dashboard so a user can upload a page image and view the converted result.

2. What The Project Uses

  • Python for the main backend and processing pipeline.
  • LangGraph to connect the pipeline steps as a state graph.
  • OpenCV for image preprocessing.
  • Tesseract OCR with English and Tamil language support.
  • Langdetect for language detection.
  • Google Translate library (googletrans) for online translation when available.
  • A local fallback dictionary for simple offline English-to-Tamil translation.
  • Google Gemini code integration through google.generativeai for optional LLM-based refinement.
  • Bleak for Bluetooth Low Energy communication.
  • FastAPI for the backend web server.
  • React, Vite, Axios, Framer Motion, and Lucide React for the frontend dashboard.
  • Pytest for unit testing.

3. Main Files and Their Roles

File or folder Purpose

pipeline.py Builds the LangGraph flow: capture, preprocess, OCR, refine, translate, encode, and vibrate.

braille_map.py Maps English and some Tamil characters into 5-bit actuator patterns.

4. How The Project Works

The project follows this flow:

  • Step 1: Capture. It gets an image from a file, a webcam, or a planned BLE camera source.
  • Step 2: Preprocess. It improves the image using grayscale conversion, contrast improvement, denoising, deskewing, thresholding, and resizing.
  • Step 3: OCR. It reads the text from the cleaned image using Tesseract OCR.
  • Step 4: Retry if needed. If OCR returns almost nothing, it retries with a different OCR page mode.
  • Step 5: Refine with LLM. If enabled, it sends the OCR text to Gemini to correct mistakes and translate to Tamil.
  • Step 6: Local translation. If the LLM step is skipped or fails, it uses language detection and then tries online translation or a local fallback dictionary.
  • Step 7: Encode. It converts the final text into a vibration command sequence.
  • Step 8: Vibrate. It simulates the pattern in the terminal or can send data through BLE to hardware.

5. What Result The Project Gives

The expected result is: image text becomes Tamil text, and then Tamil text becomes a list of 5-bit vibration commands for a Braille-like glove or tactile device.

In a real test on test_images/test_english_1.png, the pipeline successfully:

  • Read the English text from the image.
  • Produced a Tamil text result using the offline fallback translation.
  • Generated 153 vibration commands.
  • Ran the vibration output in terminal simulation mode.

So the main idea of the project works: image to text, text to translated text, and translated text to vibration sequence.

7. Does It Work Offline?

Answer: Partly yes.

  • OCR preprocessing and OCR reading can work offline if Tesseract is installed.
  • The local fallback dictionary allows a basic offline translation path.
  • The vibration simulation works offline in the terminal.
  • The real BLE camera capture is not finished. BLE capture mode is still a stub.
  • The real BLE send function exists, but the project currently uses terminal simulation in the main pipeline.

Final offline conclusion: the core demo flow works offline in a limited way, but full hardware support is not complete.

8. Does It Work Online?

Answer: Partly yes.

  • The project has an online backend using FastAPI.
  • The backend exposes routes like / and /upload-book.
  • The project has a React frontend that is designed to upload files to the backend.
  • However, the frontend build failed in this environment because of a local Vite/SWC error.
  • The online translation library is also not healthy in the current setup because googletrans is failing to initialize.

Final online conclusion: the online architecture exists, but it is not fully stable in the current environment.

9. Is LLM Integrated?

Answer: Yes, an LLM is integrated in the code.

  • The file agents/refine.py uses Gemini through google.generativeai.
  • The configuration file has USE_LLM = True.
  • The refine step is placed before the normal translation step.
  • The LLM is expected to fix OCR mistakes and translate the text into Tamil.

Current status of the LLM: not working properly now.

  • The API key in config.py is only a placeholder: YOUR_GEMINI_API_KEY_HERE.
  • The Gemini package used in the code is deprecated.
  • In testing, the LLM call waited a long time and then failed with a connection timeout.

Final LLM conclusion: yes, LLM integration is present in code, but it is not operational in the current setup.

10. Important Problems Found

  • Tamil encoding mismatch after local translation: after local translation, the state language remains english, so Tamil output is encoded using the English path. This causes many unknown Tamil characters to fall back to a default buzz pattern instead of proper Tamil mapping.
  • LLM configuration problem: the Gemini key is not set and the package is outdated.
  • Google translation problem: googletrans is installed but fails because of an httpcore compatibility issue.
  • BLE capture not complete: BLE capture mode is still marked as not implemented.
  • Frontend build problem: the React app did not build successfully in this local environment.
  • Windows console Unicode issue: Tamil printing can fail unless output encoding is set to UTF-8.

11. Benchmark Result From Existing Project Data

The file benchmark_results.csv shows mixed OCR quality. One sample image scored around 56.25%, another scored 10.53%, mixed text scored 37.5%, and the Tamil samples scored 0%.

This means the project idea is working, but the OCR quality, Tamil handling, and end-to-end reliability still need improvement.

12. Final Conclusion

BrailleAir is a meaningful assistive technology project with a clear and useful purpose. It already has a full processing pipeline, a web API, a frontend, a Braille encoding layer, and optional AI integration.

The project is partially working. The offline core demo works in a basic form. The online structure exists, but it is not fully reliable in the current environment. The LLM is integrated, but it is not working correctly now.

In simple words: the project is a good working prototype, not a finished production-ready system.

This report is based on code inspection, local verification, unit test execution, pipeline execution on a sample image, and the benchmark file already present in the project.
